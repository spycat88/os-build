# retroforge A/B image partition table.
#
# SteamOS-style atomic-update layout (cf. the steamos-teardown reference):
# a shared ESP, A/B boot partitions, A/B read-only Btrfs roots, A/B /var, and a shared
# /home. RAUC writes the inactive rootfs/var slot, then the bootloader switches on success.
#
# efi-a/efi-b are each a slot's STAGE 2 home: the ESP GRUB on the shared ESP picks a slot and hands
# over to \EFI\steamos\grub.cfg on that slot's efi partition, which boots the kernel in the slot
# root's /boot. Each carries the stage-2 config + parts.env. The stage-2 tree is ~2.3M; these are
# 128M for a filesystem reason, not a capacity one -- see the FAT block near the rows.
#
# All 8 partitions mirror the SteamOS layout exactly (esp, efi-A/B, rootfs-A/B, var-A/B, home).
#
#   p8 home  — the player user's home. Two build-time choices, neither a layout divergence:
#              it is created with an empty player home (image/lib-homestage.sh), and a factory
#              reset is a reflash of the card, and an internal UFS install is recovered by booting
#              a separate SD-card image. And home must stay LAST on disk: retroforge-grow-home
#              expands it to fill the card on first boot, so nothing may follow it.
#
# The boot partition (p1, GPT name "RetroForge") and efi-a/efi-b are ALL typed 0700 (Microsoft basic
# data), NOT ef00. Nothing in the boot chain looks for the EFI System Partition type: the stage-2
# config is reached by the ESP GRUB, not by a firmware scan, and ABL finds /EFI/BOOT/bootaa64.efi
# by CONTENT on any FAT volume it can mount (below). The role is still called "the ESP" throughout
# this tree; only its type changed.
#
# WHY NOT ef00 (2026-11-11): Windows will not assign a drive letter to an EFI System partition,
# so a card plugged into a PC showed no boot partition at all -- the one place a user might want to
# drop a dtb or read the grubenv. As basic data it mounts in Explorer like any FAT volume. GPT bit
# 63 went with it: on a basic data partition Windows reads bit 63 as "no drive letter", which
# would hide it again.
#
# MEASURED, 2026-08-24: ABL does not need the ef00 type GUID. A working ROCKNIX card's boot medium
# is not even GPT -- `lsblk -o PTTYPE,PARTTYPE,PARTFLAGS` reports `dos`, partition type `0xc` (W95
# FAT32 LBA) with the 0x80 bootable flag, carrying /EFI/BOOT/bootaa64.efi, no EFI System Partition
# type GUID anywhere on the disk -- and ABL boots it. OpenABL is the same: DefaultFiles searches
# every SimpleFileSystem handle for \EFI\BOOT\BOOTAA64.EFI and never reads the type. See
# [[abl-internal-efi-path-works]].
#
# Cards and installs made before the change carry the name RETROFORGE-ESP, type ef00 and bit 63.
# They still boot unchanged; the running system resolves either name (69-retroforge-bootdisk.rules
# links a legacy RETROFORGE-ESP at /dev/retroforge/RetroForge too), and an internal reinstall
# renames and retypes the legacy entry in place (installer/carve.sh).
#
# OpenABL's ADSP loader (Efi/UsbHost.c, ParkOtherBasicData) parks every basic data FAT volume but
# the one carrying the ADSP firmware before PIL runs, so a third basic data partition on the card is
# handled the same way efi-a/efi-b already are.
#
# systemd's gpt-auto generator ignores basic data partitions, so the ESP needs no bit 63 to keep
# it from being auto-mounted at /efi (the name the initramfs reserves for the SLOT's efi-a/b
# partition). Its one and only mount definition is the /esp entry rootfs/assemble-rootfs.sh puts in
# /etc/fstab.
#
# Root slots are 2G. They carry the OS (gamescope session, shell, emulators, firmware, modules).
# The root is sealed read-only and baked with zstd (assemble-rootfs.sh), so content compresses well.
#
# Size against the image's APPARENT size, not its content. mkfs.btrfs --shrink cannot pack
# below its block-group granularity, so the image reports ~2G more than it actually occupies
# (measured 2026-07-27 on the reference build) — and the apparent size is what has to fit the
# partition. make-sdcard.sh's `fits` check fails the build when an image outgrows its slot.
#
# The 7G the reference build used was sized for ~2.9G of x86-emulation payload (a FEX guest
# rootfs and two Proton builds) on top of ~0.8G of OS; none of that ships here. Re-measure
# `du --apparent-size out/images/rootfs.img` whenever a large package lands and keep at least
# ~1G of headroom under the slot: 4b needs room for a bundle to land next to a running system.
#
# 4G -> 2G on 2026-10-03, after dropping sddm/Qt6, ffmpeg and noto-fonts-cjk took the image to
# ~1.0G apparent (from ~3.1G). Emulators ship as AppImages that bundle their own Qt/ffmpeg, so
# that runtime does not come back as root packages. Devices flashed with 4G slots keep them: RAUC
# writes a smaller image into a larger slot fine, so this only changes newly flashed/installed cards.
#
# Emulators and the shell are versioned OS components and stay INSIDE the root slot rather than
# on a shared partition: sharing them across slots would let an update mutate the running
# system and break rollback.
#
# 'rest' expands to fill the target device. Fixed partitions total ~5.0G, so the minimum
# usable card is 16G (leaving ~10G of /home); 64G+ is the sane target for ROMs.
#
# 'attrs' is a comma-separated list of GPT attribute bits to set, or '-' for none. Only bit 63
# ("no-auto") is used today, on home alone. home carries the discoverable "Linux /home" type GUID
# (8302) because systemd-repart matches it by that GUID to grow it on first boot — matching by
# type is what guarantees repart can never touch a root partition. But that same GUID also makes
# systemd's gpt-auto generator synthesize its OWN home.mount, which would silently shadow (or be
# shadowed by) the one /etc/fstab already declares, with different options and no growfs. Bit 63
# tells gpt-auto to skip the partition while leaving the type GUID — and so repart — intact.
#
# Consumed by image/genpart.sh to emit an sgdisk script. Row order = partition number.
#
# EVERY FAT FILESYSTEM HERE IS CREATED FAT32 *OR* FAT16, CHOSEN FROM THE DISK'S GEOMETRY, and
# lib-slotwrite.sh's fat_type_for() is what chooses. Do not "simplify" it back to a forced -F 32.
#
# A FAT32 needs at least 65525 data clusters to BE a FAT32, and cluster count scales with SECTORS,
# not bytes. These partitions are sized in bytes, so the same row is a different filesystem on media
# with different logical sector sizes:
#
#                       512-byte sectors        4096-byte sectors
#   esp  256M           516190 clusters  FAT32   65376 clusters  too few for FAT32
#   efi  128M           258078 clusters  FAT32   32672 clusters  too few for FAT32
#   efi   64M (was)     129022 clusters  FAT32   16320 clusters  too few for FAT32
#
# Every SD card is 512e and every internal UFS in this fleet is 4Kn, so a forced -F 32 produced a
# valid filesystem on every card ever flashed and an invalid one on every internal install. Nothing
# offline can catch it either: make-sdcard.sh formats inside an IMAGE FILE, where mkfs.vfat sees
# 512-byte sectors whatever the eventual target is, and so does every test fixture.
#
# MEASURED on an AYANEO Pocket ACE, 2026-08-21, and it cost an evening because it surfaces as two
# unrelated-looking failures:
#   esp at 256M   ABL's own FatPkg refuses the volume (EFI_VOLUME_CORRUPTED, EnhancedFatDxe/Init.c
#                 checks MaxCluster < 65525), never produces a SimpleFileSystem handle for it, and
#                 LoadEFI reports "Failed to load EFI: Not Found" without reading a byte of it.
#   efi at 64M    the ESP is fine, ABL loads stage 1, and steamcl (stage 1 then) could not mount
#                 efi-A/B for the same reason -- so it found no boot candidate and printed "Boot
#                 failed, waiting 5s".
# Both are the same defect. The fix is the filesystem TYPE, not the partition size: growing the ESP
# to 512M also worked, and was reverted, because it wasted space to buy what FAT16 gives for free.
#
# efi-a/efi-b ARE 128M rather than 64M, and that IS about size: at 64M/4Kn even FAT16 lands 7
# clusters above the FAT12 boundary, which is a margin decided by mkfs.fat's reserved-sector
# arithmetic rather than by us. 128M gives 8188 -- twice the floor. The content is ~2.3M either way.
#
# tests/test-partition-table.sh asserts all of this against the table alone, at both sector sizes.
#
# name      size  typecode  fs        label            attrs
esp         256M  0700      vfat      RetroForge         -
efi-a       128M  0700      vfat      retroforge-efi-A   -
efi-b       128M  0700      vfat      retroforge-efi-B   -
rootfs-a    2G    8300      btrfs     retroforge-root-A  -
rootfs-b    2G    8300      btrfs     retroforge-root-B  -
var-a       256M  8300      ext4      retroforge-var-A   -
var-b       256M  8300      ext4      retroforge-var-B   -
home        rest  8302      ext4      retroforge-home    63
